## 60秒简单版

想象一个有32名专家的维修店。

今天的人工智能模型的工作方式是这样的：**每一项工作都同时交给所有32个人处理**。每个人都处理每项工作。这种方法可行，但也极其浪费。

我重建了一个50亿参数人工智能模型的部分代码（[SpikingBrain 2.0](https://github.com/BICLab/SpikingBrain2.0)），使得一位接待员先阅读每项工作，然后将其转交给**应该处理它的那一位专家**。

同样的店。同样的32位专家在名单上。产出的工作质量相同。

**工作量只有三十二分之一。**

这就是整个概念。这篇文章的其余部分讲述的是我正确测量它时发生的事情——包括我必须扔掉的那一个结果。

## 什么是混合专家（Mixture-of-Experts）模型？

在普通的神经网络中，每个输入都通过每个参数。这是一个巨大的单一函数，每次执行时都会运行所有代码。

**混合专家（MoE）**模型将这个大函数分成许多较小的函数——"专家"——并在前面放置一个**路由器**。路由器查看每个单词，并选择处理它的专家。

通过**Top-1路由**，每个单词恰好由一位专家处理。不是两位，不是混合。就是一位。

重点是：**当你添加更多专家时，每个单词的成本不会改变。** 64位专家的成本与8位相同，因为你仍然只运行其中一位。但每次添加一位专家时，模型的总容量都会增长。

这不是任何人发现的聪明技巧。这只是算术。这正是为什么它是可信的。

## SpikingBrain 2.0是什么？

[SpikingBrain 2.0](https://github.com/BICLab/SpikingBrain2.0)是来自中国科学院自动化研究所的开源脑启发模型系列。两个5B模型，发布时包含代码和权重。

这是真正有趣的工作。它用稀疏softmax注意力和稀疏线性注意力的混合替换了标准注意力，添加了支持事件驱动硬件的激活编码方案，并提供了一个转换流水线，可以将现有的Transformer转换为这种架构。

我阅读了他们发布的代码而不仅仅是论文，并找到了我需要的切入点：**每个块都是`attention → dense feed-forward`。** 在整个发布版本的前馈层中，没有专家路由。

所以稀疏MoE前馈不是与他们想法相竞争的概念。这是一个**空白的位置**。

## 我添加的内容

四个机制，来自[我自己的研究仓库](https://github.com/JustinGuese/S2-MoE-llm)并移植到他们的块中：

- **一个Top-1路由的专家池**，替换密集的前馈层。
- **一个始终开启的共享核心**——一位小型专家，每个单词都会通过，以及路由的专家。
- **一个分组GEMM CUDA内核**，因为没有它整个东西会更慢（下面有更多介绍）。
- **一个密集到MoE的升级器**，使得专家池可以从他们的**现有训练权重**构建，而不需要从头重新训练。

所有这些都隐藏在他们所有六个发布配置中不存在的配置键之后。**他们发布的检查点在不主动启用的情况下按字节加载并运行得完全一样。** 有一个测试声明了这一点。

## 结果：相同的质量，1/32的前馈计算

这是核心测试。

在**参数数量相匹配的情况下**——稀疏模型为77.8M对比密集控制的77.7M，相差0.2%——稀疏模型达到**相同的验证困惑度**，同时运行**1/32的前馈计算**。

这是**每单位活跃计算精度提高32倍**。

相同的大小。相同的质量。该层中只有三十二分之一的工作。

这正是稀疏MoE命题的工作方式：容量随着池的增长而增长，活跃计算保持平稳。

## 在他们的5B规模上的价值

计算声明由张量形状而不是训练确定——所以它们可以在SpikingBrain的真实5B块尺寸上直接测量，使用随机权重，在单个RTX 4090上花费大约20分钟。

在`hidden_size 2560`、`intermediate_size 9728`、bf16、参数匹配、batch 8 × sequence 512的条件下：

| 前馈层                    | MFLOP/token | mJ/token | Active watts | Tokens/sec  |
| ----------------------- | ----------- | -------- | ------------ | ----------- |
| Dense SwiGLU (their code) | 229.1       | 0.669    | 298.5        | **446,070** |
| Sparse MoE, 16 experts    | 89.1        | 0.419    | 138.9        | 331,697     |
| Sparse MoE, 32 experts    | 84.5        | 0.412    | 133.7        | 324,344     |
| Sparse MoE, 64 experts    | 82.3        | 0.414    | 123.7        | 299,053     |

**每个块少2.71倍的FLOPs。每个token少1.62倍的能量。功率消耗不到一半**——134 W对299 W。

## 为什么1/32没有转化为32倍的整体提升

再看一遍那个表。前馈计算下降了32倍，但整个块只下降了2.71倍。其余的去哪里了？

**始终开启的部分不会缩小。** 注意力仍然在每个单词上运行。路由器在每个单词上运行。共享核心在每个单词上运行。

优化一个组件只能节省该组件的份额。一旦前馈层几乎免费，其他一切就成为下限——你已经达到了前馈稀疏性能做到的上限。

如果从这篇文章中为你自己的工作取一个数字，就取这个。它告诉你何时停止优化这个层并去看另一个。

## 诚实的部分：密集模型更快

正确阅读每秒token列。**密集模型446,000 vs 稀疏模型324,000。** 密集模型以舒适的优势获胜。

这里的胜利是**FLOPs和功率，而不是时钟周期吞吐量**。

原因很不起眼：一个宽密集矩阵乘法使用GPU的方式比分组矩阵乘法加上路由器加上共享核心更好。GPU是为大型规则算术块而设计的。

在功率受限或事件驱动硬件上，这种权衡会反转，稀疏模型获胜。在面向吞吐量的数据中心GPU上，它不会。任何对此进行基准测试的人都会在十分钟内发现这一点，所以没有理由假装情况并非如此。

## 没有合适的CUDA内核，稀疏模型会更慢

这是我最希望另一位工程师能从中获得启发的部分。

明显的实现在Python中遍历专家——一次迭代，每个都启动一个内核。该开销对每位专家是固定的，所以它增长速度与你的节省完全相同。

**单独测量时，朴素稀疏层在每个专家数量上都比密集更慢。** FLOP节省存在于纸上，绝对不存在于其他任何地方。

修复方法：按分配给他们的专家对token进行排序，形成连续块，并对所有块进行一次分组矩阵乘法。我用明确的反向传播将`torch._grouped_mm`包装在一个自动梯度函数中，使其在训练中也能工作。

| 专家数量                | 8     | 16    | 32    | 64         |
| ---------------------- | ----- | ----- | ----- | ---------- |
| Forward vs Python loop | 2.27× | 4.60× | 8.29× | **12.75×** |
| Training step vs loop  | 1.85× | 3.99× | 6.34× | **9.95×**  |

它是**位精确的**——输出和两个权重梯度对比循环的最大绝对差差为零。这是纯开销去除，而不是近似。

**一个没有内核的高效架构就是一个较慢的架构。** FLOP计数是一个承诺；内核是是否支付的方式。

## 一个CUDA错误，会默默地挂起你的GPU

如果你曾经接触这个操作，值得知道：**`torch._grouped_mm`在退化的组拆分上死锁**。

当专家占用不均匀时，你会得到零宽度段。将这些输入内核，它会挂起——GPU空闲，一个CPU核心旋转，没有错误，没有超时。看起来完全像一个缓慢的训练步骤，直到你注意到它已经缓慢了六个小时。

在调用之前将空组压缩出来在数学上是相同的，并完全移除触发器。

## 稀疏性在批处理服务中是否存活？

这里有两个不同的声明经常被混淆，所以让我们分开它们。

**每个token的FLOPs在任何批大小下都保持在1/32。** 无论有多少单词在处理，每个单词都恰好通过一位专家。上面的表在batch 8下测量——这些已经是批处理的数字。

**批大小中崩溃的是专家_驻留_**——在内存中仅保留活跃专家的能力。在batch 1，你接触一位32中的专家，可以跳过其余的。在batch 64，跨批接触的专家的**联合**涵盖大部分池：

| 批大小     | 1     | 32    | 64    |
| -------------- | ----- | ----- | ----- |
| Union sparsity | 96.9% | 39.7% | 14.1% |

所以专家卸载和事件驱动权重门控是**单流命题**。计算和能量减少不是——这些在批处理下保持不变。

这种区分是为什么"上下文稀疏性"方法不断无法达到生产服务栈的原因，以及为什么精确说明你声称的是这两个中的哪一个是值得的。

## 我删除的结果：一个随机种子删除了2.1%的胜利

现在是不舒适的部分。

我也有一个**质量**胜利。稀疏模型以2.1%的困惑度击败了它的密集控制——58.99对60.27。不错的数字。它进入了写法。

然后我运行了另一个种子来获得误差条。

胜利消失了。第二个种子：**58.52对58.54。** 完全平手。

这实际上发生了什么。**密集基线**在种子之间移动2.9%（60.27→58.54）。我的模型移动0.8%（58.99→58.52）。第一个种子没有显示我的模型做得很好。它显示了**基线做得很糟糕**。

在两个种子上，间隙是−1.1%，±1.05百分点的传播。与平价无法区分。

**这个教训一般化：你的基线也有差异。** 单种子比较不衡量你的方法——它衡量两个模型的运气。我甚至事先写下了规则（"一个种子，任何低于百分之几的东西都不是结论"），而2.1%恰好坐在线上，这正是此类规则停止装饰的地方。

核心结果——以1/32计算为单位的平价——从未受到影响。失去奖励不会删除主菜。但2.1%已经消失，不会回来。

## 其他什么不起作用

四个机制中的两个没有价值，报告这比让其他人发现它更便宜。

**尖峰激活在相同计算下成本2.8%的困惑度。** 二进制0/1激活产生真正的激活稀疏性——但密集的GPU内核无法实现它。所以在这个硬件上它是纯粹的质量成本。它的价值是与事件驱动神经形态芯片的兼容性，这是一个真实的论点，只是不是准确性或GPU效率的论点。

**睡眠阶段与共享核心相比是惯性的。** 它在训练期间重新构建专家池——合并重复、修剪、重新增长。结果：−0.28%困惑度，额外5.2%的训练时间。日志解释原因：在所有十个周期中，它没有合并任何东西。**始终开启的共享核心正好吸收了合并存在的冗余。** 两个机制做相同的工作，所以第二个没有任何东西可以做。

**即使是共享核心也是一个权衡，而不是免费的胜利**——它以52%更多的活跃前馈计算购买2.5%的困惑度。如果你优化质量是值得的，如果你优化计算就不是。

## 他们发布的设置中的两个错误

按照他们在干净机器上的自己安装说明，两件事坏了。一旦你知道两个都很琐碎，如果你不知道两个都花一个小时：

**他们的捆绑MoBA仍然pin `flash-attn==2.6.3`。** 安装它默默卸载他们的说明在一行前要求的`flash-attn==2.7.3`，然后无法从源代码构建2.6.3。使用`--no-deps`安装修复它，并与他们自己的说明相匹配，即捆绑副本已适应较新的接口。pin是陈旧的元数据。

**`import fla`需要C编译器和Python头文件。** Triton在导入时编译启动器存根。在没有`build-essential`和`python3-dev`的最小CUDA映像上，它只是死亡。

## 审计他们的机制而不是我的

我构建的最有趣的东西不是MoE。这是**他们**架构的诊断。

他们的稀疏线性注意力每个单词选择4个状态分区中的2个，通过辅助损失训练以实现平衡使用。该损失仅在训练期间运行。**没有什么保证平衡在发布的权重中存活**——而且两种失败方式都不会在困惑度或基准分数中显示：

- **使用崩溃**——一些分区获得大多数选择，所以扩展状态的有效规模小于配置的，其内存成本购买的少于宣传的。
- **输入独立性**——使用看起来整体平衡，但每个单词都选择了**相同的**对。直方图看起来完美，同时路由不携带任何信息。

测量这个有一个陷阱。使用`trust_remote_code=True`加载模型导入模型**捆绑在检查点目录中**的建模代码，而不是仓库中的副本。修补仓库的模块，你测量模型从未调用的东西，并获得一个看起来有信心的虚无表。

结果，在检查点的完整训练上下文范围内：

| 上下文长度   | 1,024  | 4,096  | 8,192  |
| ---------------- | ------ | ------ | ------ |
| Usage entropy    | 0.9868 | 0.9868 | 0.9863 |
| Most-common pair | 25.7%  | 26.2%  | 26.5%  |
| All 6 pairs used | yes    | yes    | yes    |

熵1.0表示完全平衡。16.7%的份额意味着完全均匀分布在对中。

**两种失败模式在每个长度上都不存在。** 在8倍上下文增加上，熵移动0.0005。他们的辅助损失完成了工作，财产得以保持。

这是一个零结果，我正在报告它作为一个。现在它是[他们仓库上的开放讨论](https://github.com/BICLab/SpikingBrain2.0/issues/4)。

## 诚实的范围

上面的一切，有限制：

- **没有什么在5B或他们的检查点上训练过。** 质量工作在≤146M参数，从头开始。5B数字是块级别和形状确定的。
- **质量结果是一到两个种子。** 一个已经崩溃了。方向是发现；幅度是初步的。
- **质量边缘在长训练预算下反转**——固定预算的−5.15%优势在4倍预算处变为+2.4%。[我单独写了它](/blog/s2moe_budget_dependent_benchmarking/)。SpikingBrain的训练远超过该点。
- **GPU上的能量真的是FLOPs除以延迟。** 功率在架构中差异很小，所以可防御的框架是每个token的服务成本，而不是原始焦耳。真实的事件驱动能量会计需要我还没测量的神经形态硅。

## 什么成立

- **匹配参数的平价，以1/32的活跃前馈计算。** 每单位活跃计算精度提高32倍。
- **每个块少2.71倍的FLOPs，每个token少1.62倍的能量**，在他们的真实5B块形状，来自随机权重。
- **分组GEMM内核是使它成为真实的东西**——位精确，比朴素循环快12.75倍。没有它稀疏模型比密集更慢。
- **一个值得知道的上限：** 前馈稀疏只能节省你前馈的份额。之后始终开启的部分就是下限。
- **一个经过验证的诊断**，用于SpikingBrain自己的分区路由，回来是健康的。

## 常见问题

**混合专家真的减少计算吗？**
是的，而且减少量是可预测的。Top-1路由无论池大小如何每个token运行一位专家，所以前馈计算是参数匹配密集层的`1/n_experts`。在32位专家处测量为1/32，一旦计算始终开启的部分，就会变为整个块少2.71倍的FLOPs。

**稀疏MoE模型比密集模型快吗？**
不一定，这里也不是——324k tokens/sec对比密集的446k。更少FLOPs不等于更低延迟。胜利是FLOPs和功率消耗（134 W vs 299 W），而不是吞吐量。

**MoE稀疏性在批处理服务中是否存活？**
计算节省是的——每个token仍然遍历一位专家，无论批大小如何。什么不存活的是专家**驻留**：整个批中接触的专家的联合从batch 1处的96.9%稀疏进行到batch 64处的14.1%，所以专家卸载是单流技术。

**尖峰激活改善准确性吗？**
不在这个测量中。他们在相同计算下成本2.8%困惑度。该好处是与事件驱动神经形态硬件的兼容性，不是准确性或GPU效率。

**你需要多少个种子来声称质量改进？**
超过一个，这篇文章是警示故事。一个2.1%的优势在第二个种子上消失了，因为**密集基线**已经抽到了一个坏种子。单种子比较衡量运气，而不是方法。

**你可以将现有的密集模型转换为混合专家吗？**
是的——这就是升级器所做的。它从训练的密集前馈权重的切片初始化每位专家，而不是从头开始。这是一座权重初始化桥梁，仍然需要继续训练来恢复质量；这不是免费转换。

```bash
git clone https://github.com/JustinGuese/SpikingBrain2.0-s2moe
cd SpikingBrain2.0-s2moe

# Energy and FLOPs at SpikingBrain's real 5B block shape - random weights, no training
python spb2/s2moe/bench/bench_energy.py --n-experts 32 --param-match
python spb2/s2moe/bench/bench_active_flops.py --n-experts 32

# Kernel equivalence and speedup, forward and training
python spb2/s2moe/bench/bench_dispatch.py

```
